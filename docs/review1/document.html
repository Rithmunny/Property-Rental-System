3. Corrected Proposal Summary

3.1 Approved problem

Property owners in Phnom Penh who manage rentals through phone calls, Facebook, Telegram or paper records face delayed replies, inaccurate availability and double allocation of the same unit. Tenants must contact many landlords one by one to compare price, location and facilities. Classified sites list inventory but leave booking, payment and records off-platform (Bamboo Routes, 2026; Realestate.com.kh, 2026).

3.2 Aim

To design and develop a web-based Property Rental System for the Cambodian long-term rental market that centralises listing, online rental requests (booking), role-based dashboards and, later in the semester, sandbox payment and AI-assisted recommendations.

3.3 Objectives (unchanged in intent; delivery dates updated)

  1. Analyse landlord and tenant needs for listing, requesting/booking and payment.
  2. Design a PostgreSQL schema (Supabase) for users, listings, requests, contracts, payments and reviews.
  3. Implement authentication and dashboards for tenant, landlord and administrator.
  4. Implement a request-to-rent workflow that prevents a second accepted occupancy on the same listing.
  5. Integrate a payment gateway in sandbox mode (ABA PayWay or Stripe) after the core path is stable.
  6. Integrate an AI recommendation feature (OpenAI or Gemini) after the core path is stable.
  7. Test, document and complete the project by 7 November 2026.

3.5 Technology correction

The proposal named Next.js. The implemented presentation layer is a Vite 6 + React 19 single-page application with Tailwind CSS. The team keeps this stack because the public site and three dashboards already exist and the API seam (frontend/src/api) was written for a backend handoff. Database, auth and (later) storage remain Supabase / PostgreSQL as approved. Maps already use Leaflet / OpenStreetMap, which the proposal allowed as a free fallback.

3.6 Users

Primary: tenant (renter) and landlord (owner). Stakeholder: administrator. Secondary (not implemented as a role): property-management staff acting on behalf of a landlord.

4. Expanded Literature and Existing-System Analysis

Rental software sits at the intersection of classified advertising, property management systems (PMS) and consumer booking platforms. Sommerville (2016) treats requirements as testable statements traced through design and implementation; this package follows that discipline. Role-based access control is the standard way to separate tenant, landlord and operator privileges in a multi-sided platform (Ferraiolo et al., 2001).

4.1 Comparable systems

Table 4.1 — Critical comparison
SystemStrengthsLimitations for this projectImplication

Facebook Marketplace / groups and Telegram channelsZero cost; landlords already present; fast posting.Unstructured; stale posts; no availability lock; high fraud and double-booking risk; no audit trail.This is the current process the problem statement attacks.

4.2 Technical literature used in the design

  • Backend-as-a-service (Supabase) provides managed PostgreSQL, Auth and Row Level Security, which matches a two-student schedule (Supabase, 2026).
  • SPA + BaaS is an accepted architecture when the UI is rich and the data API is relational (MDN Web Docs, 2026).
  • Payment platforms (ABA PayWay, Stripe) must stay in sandbox for student projects; live settlement is out of scope (Stripe, 2026).
  • LLM recommendation APIs can rank listings from preferences and history, but they need seed volume and a rule-based fallback (OpenAI, 2026). That is why AI is Must for the semester and not the Review 1 demo.

4.3 Project gap

Existing Cambodian channels help a tenant find a phone number. They do not give a shared, role-protected record of “this person asked to rent this unit, the owner accepted, the unit is no longer available.” The Property Rental System closes that gap with listings, a rental-request workflow, later sandbox payment, and later AI ranking, which together provide the technical depth Review 0 required (booking-conflict logic, payment workflow, AI integration) without claiming all three are finished on 27 August.

5.3 Domain research

Phnom Penh condominium stock has grown toward about 80,000 units, and classified portals already carry tens of thousands of advertisements (Bamboo Routes, 2026; Khmer Times, 2025; Realestate.com.kh, 2026). Scale supports a software solution; it does not by itself supply booking integrity. That integrity is a product requirement, not a marketing page.

5.4 Questionnaire (instrument)

A 12-item questionnaire (Appendix A) covers search behaviour, willingness to request online, payment trust, and landlord record-keeping. It will be issued to at least eight participants (mix of tenants and landlords) before Review 2. Until those returns are in, design uses Table 5.2 plus the approved proposal evidence. The group will not invent named interview transcripts.

5.5 Key findings used in design

  1. The primary tenant job is compare-then-contact; the system must make compare (search) and contact (request) first-class.
  2. The primary landlord job is an inbox, not a public blog.
  3. Payment and AI add depth but fail if the request state machine is missing — hence Review 1 focus.
  4. Admin exists because unmoderated classifieds were observed to be noisy.

8.1 User stories and acceptance criteria (core)

US-01. As a tenant, I want to log in so that I see only the tenant dashboard.
Acceptance: Valid demo tenant credentials open /dashboard/tenant. Invalid password shows an error. Opening /dashboard/landlord redirects away.

US-02. As a tenant, I want to request to rent a listing so that the landlord receives a pending request.
Acceptance: After submit, a rental_requests row exists with status pending. Repeating the same listing shows the existing request rather than a duplicate rent row.

US-03. As a landlord, I want to accept a request so that the tenant sees accepted and the listing is no longer offered as available.
Acceptance: Status accepted; contract stub present; listing available is false; tenant refresh shows accepted.

US-04. As a landlord, I want to add a listing so that tenants can find it in search.
Acceptance: New row with landlord_id = current user; appears on /rent after reload from the database.

US-05. As an admin, I want to suspend a landlord so that the account cannot operate as active.
Acceptance: Status change persists; only admin role can call the update.

US-06. As a tenant, I want to save a home so that I can open it later from Saved Homes.
Acceptance: Toggle writes saved_properties; list matches after logout/login.

15. Security and Privacy Design

  • Authentication. Supabase Auth, email/password, JWT stored as the existing session shape { user, token } under the documented localStorage key only as a client cache of a server session.
  • Authorisation. RequireRole for routes; RLS for tables. Landlords cannot update another landlord’s listing. Tenants cannot accept requests.
  • Admin. Seeded account only. Register UI offers tenant and landlord. Mock role picker is development-only.
  • Validation. Required fields, email format, price > 0, status enum, UUID identifiers. Server (RLS + check constraints) is authoritative.
  • Data protection. No full card numbers. Demo personal data is synthetic. Production would add HTTPS only, which Supabase already uses.
  • Configuration. Anon key is a publishable client key with RLS; service role key never ships in the Vite bundle.
  • Privacy. Collect name, email, optional phone/Telegram. Purpose: account and rental coordination. Retention: project duration plus thesis archive. Cambodia’s personal-data expectations are treated as data minimisation and no unnecessary ID scans (out of scope: title registry).

Chapter 1 — Introduction (draft)

Long-term rental in Phnom Penh is still coordinated largely through social posts and messaging applications even though the city’s housing stock and classified inventory are large (Bamboo Routes, 2026; Realestate.com.kh, 2026). Landlords lack a single register of availability and applicants; tenants repeat the same questions to many owners. This thesis reports the design and development of a web-based Property Rental System that provides listing management, a rental-request workflow, role-based dashboards and, in later iterations, sandbox payment and AI-assisted recommendations.

Problem. Manual, fragmented coordination causes delay, double allocation and weak comparison. Aim. Deliver a working system that centralises those jobs for tenant, landlord and administrator. Objectives are the seven statements in Section 3.3. Scope is the in-scope list in Section 3.4; exclusions include live payments, legal contract generation, land-title APIs and native apps. Appendix A — Questionnaire instrument

Title: Property rental search and booking (academic, B11-G06). Time: 8–10 minutes. Consent: voluntary, anonymous, for the final-year project only.

  1. Role: tenant / landlord / both.
  2. How do you usually find or advertise a rental? (Facebook, Telegram, website, agent, other).
  3. About how many separate chats or calls does a typical search take?
  4. Have you experienced a listing that was already taken after you agreed? Yes / No / Not sure.
  5. Would you submit a “request to rent” inside a website if you could see the status (pending/accepted)? Yes / Maybe / No.
  6. How important is seeing the same unit’s price, photos and map together? 1–5.
  7. Would you pay a deposit through a known sandbox or test payment page for a student project demonstration? Yes / No.
  8. As a landlord, what is hardest: photos, answering chats, tracking applicants, collecting rent, other.
  9. Which filters matter most? Location, price, type, furnished, parking (rank top 3).
  10. Would personalised suggestions help if they were clearly marked as suggestions? Yes / No.
  11. What would stop you from using such a site? Trust, fees, Khmer language, mobile, other.
  12. Any comment.
